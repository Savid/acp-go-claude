---
title: "Elicitation"
description: "Forward Claude's user-facing questions to clients that opt in during initialize"
---

When Claude needs to ask the user a free-form question mid-turn, the adapter can
forward it to the host as an ACP elicitation request. This is how Claude's
`AskUserQuestion`-style prompts reach the person driving the session.

## Capability gating

Elicitation is only used when the client advertised elicitation support during
ACP initialize. The adapter checks that capability before sending anything, so a
client that never opted in is never handed an elicitation request it cannot
render.

| Client elicitation capability | Adapter behavior |
| --- | --- |
| Advertised | Claude's question is forwarded as an ACP elicitation request. |
| Absent | No request is sent; Claude receives a bounded failure and the turn continues or stops per Claude's own logic. |

<Note>
Elicitation is not the permission channel. Tool-access approvals always use
[permission prompts](/docs/features/permissions); elicitation carries free-form
questions only.
</Note>

Because behavior depends on the client's advertised capability, test both paths:
a client that supports elicitation and one that does not.

## Route correlation

The initialize response advertises
`_meta["acp-go.dev/route"] = {"versions":[1]}`. Every emitted form or URL
elicitation carries version 1, the owning `sessionId`, the current
`turnNonce`, and exactly one callback correlation (`toolCallId` or
`requestId`) under that reserved key. Existing non-reserved metadata is
preserved. A pre-existing reserved key fails the callback closed.
