Goals are a Claude-specific incubation surface for hosts that want a durable
session objective. They are exposed as `_meta.claude.goal`, not as portable ACP
core state.

## Shape

```json
{
  "objective": "Ship OAuth login",
  "completionCondition": "Browser login works and tests pass",
  "status": "active",
  "createdAt": "2026-05-27T00:00:00Z",
  "updatedAt": "2026-05-27T00:00:00Z",
  "completedAt": null,
  "reason": null,
  "reasonCode": null,
  "goalId": null,
  "source": "client"
}
```

Statuses are `active`, `completed`, and `blocked`. Clients may set `active` or
`blocked`; `completed` is produced by Claude-native goal rows or future adapter
logic. `source` is `client` for adapter-owned goals and `claude` for native
Claude `/goal` state mapped from transcript mirror rows.

Non-list goal output is a full snapshot. Optional fields are emitted as explicit
`null` values so ACP `session_info_update._meta` recursive merge semantics clear
stale nested fields. `session/list` uses a compact summary with only
`objective` and `status`.

Client input accepts `objective`, `completionCondition`, `status`, and
`reason`. `objective` is required for non-null goals and must be at most 4096
bytes after trimming. `status` defaults to `active` and may be only `active` or
`blocked` in client input. Canonical output fields such as `createdAt`,
`updatedAt`, `completedAt`, `goalId`, and `source` are tolerated on input so
hosts can round-trip snapshots, but the adapter owns their stored values.
Non-null `reasonCode` is rejected because reason codes are adapter-owned.
`session/list` summaries truncate `objective` to 256 runes.

## Set Or Clear

Use the extension method `_claude/session/setGoal`:

```json
{
  "sessionId": "00000000-0000-4000-8000-000000000000",
  "goal": {
    "objective": "Ship OAuth login",
    "completionCondition": "Browser login works and tests pass",
    "status": "active"
  }
}
```

Clear with:

```json
{
  "sessionId": "00000000-0000-4000-8000-000000000000",
  "goal": null
}
```

Setting or clearing a goal updates adapter-owned session metadata immediately
and emits `session_info_update._meta.claude.goal`. It does not cancel,
interrupt, restart, or send `/goal` to Claude. If Claude is mid-turn, the goal
change is UI/session metadata until a future prompt or native Claude `/goal`
command changes Claude behavior.

## Session Lifecycle

`session/new`, `session/load`, `session/resume`, and `session/fork` accept
initial goal metadata at `_meta.claude.goal`. Lifecycle responses include the
current goal under `_meta.claude.goal`; when no goal is known, the value is
`null`.

`session/load` replays transcript updates first, then emits the latest known
goal metadata before returning when the transcript contains native goal rows.
`session/resume` does not replay history, so non-active native goals may not
have a cheap summary.

`session/list` includes `_meta.claude.goal` only when the adapter already knows
the goal cheaply, usually for active in-memory sessions.

## Native Claude Mapping

The adapter launches Claude with `--session-mirror` so native `/goal` transcript
mirror rows can be observed even when no external `SessionStore` is configured.
Goal extraction runs before optional store append and before transcript path
resolution.

Native `attachment.type == "goal_status"` rows map as follows:

| Claude row | Adapter goal |
| --- | --- |
| `condition` | `objective` and `completionCondition` |
| `met: false` | `status: "active"` |
| `met: true` | `status: "completed"` and `completedAt` |
| `failed: true` | `status: "blocked"`, `reasonCode: "native_failed"` |
| stop-hook override/cap near `met: true` | `status: "blocked"`, `reasonCode: "stop_hook_override"` |

Native clear is currently detected from version-probed Claude local-command
text such as `Goal cleared:` or `No goal set`, correlated with a `/goal clear`
command row. This is intentionally covered by live integration tests because
the CLI surface is undocumented and may change.

## Privacy

Goal objective and reason text are not recorded as metric labels or span
attributes by the adapter. They are emitted only through ACP metadata requested
by the host and through raw Claude events when raw event emission is enabled.
