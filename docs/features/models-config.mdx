Session-lifecycle responses expose the selected model under
`_meta.claude.modelId`, its current effort variant under
`_meta.claude.variant`, and selectable variants under
`_meta.claude.availableVariants`. Each model option may additionally carry
`_meta.claude.supportedEffortLevels`, `_meta.claude.supportsAutoMode`, and
the positive token limits `_meta.claude.contextWindow` and
`_meta.claude.maxOutputTokens` when its discovery source supplies those facts.

## Model catalog

For direct Anthropic sessions with an unambiguous `CLAUDE_CODE_OAUTH_TOKEN` or
`ANTHROPIC_API_KEY` in the effective launch environment, the adapter reads
[`GET /v1/models`](https://platform.claude.com/docs/en/api/models/list) from
`https://api.anthropic.com`. The API supplies model IDs, display names, input
and output token maxima, and supported effort values. Native aliases and
configured `availableModels` restrictions still apply; exact native effort
choices and explicit effort refusals take precedence. A model missing from
Claude Code's picker can appear through the API; an explicitly disabled native
model remains excluded. Native family allowlists such as `["sonnet"]` include
permitted versions throughout that model family. A specific version or full-ID
entry for the same family narrows its wildcard according to [Claude's allowlist
merge rules](https://code.claude.com/docs/en/model-config#merge-behavior).

Reconciliation and capability lookups use exact model IDs and native
`resolvedModel` identities. Selecting a full ID keeps the native effort and
auto-mode facts reported by an alias resolving to that ID, including when
direct API discovery is disabled. The requested ID remains unchanged.
An unknown full model ID is sent unchanged unless an explicit
`CLAUDE_MODEL_CONFIG.modelOverrides` mapping replaces it; a similar model name
or version does not substitute for it. Claude Code alone supplies
`supportsAutoMode`.
API token maxima are catalog metadata: runtime `usage_update.size` stays
unknown until the native session reports its context window. Model listings
publish no modality fields or per-model `capabilities` array. Catalog presence
does not establish successful inference, quota, or billing entitlement.

### Routing and credentials decide which names are published

Claude Code reports the provider it resolved, and every provider it names —
Bedrock, Vertex, Foundry, and the rest — serves Anthropic's models under its own
account. Their menus stand exactly as Claude Code reports them. A provider
Claude Code will not name leaves the route unestablished, and an unestablished
route is no evidence that Anthropic's own names dispatch, so they are withheld.

The process whose menu does not describe its endpoint is a first-party one
pointed somewhere else. The test is Claude Code's own, and the hostname alone
decides it: `ANTHROPIC_BASE_URL` naming a host other than `api.anthropic.com`
or `api-staging.anthropic.com`, whatever scheme, port, path, or query it
carries, and whether it comes from the launch environment or from a settings
file's `env` block, which Claude Code applies over it. Such an endpoint speaks
the Anthropic API without serving Anthropic's models, so every row whose
dispatch identity is one of them is withheld: a `claude-` prefixed ID, and the
`default`, `sonnet`, `opus`, `haiku`, and `fable` aliases when nothing else is
resolved behind them. Rows resolving to another ID stay, and a model Claude Code
explicitly refused stays too, so an allowlist or an explicit selection cannot
reintroduce it. Setting `_CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL` to `1`,
`true`, `yes`, or `on` declares the endpoint first-party instead: Claude Code
then serves its own menu and runs no gateway discovery, and nothing is withheld.

A process holding no credential withholds the same names for the same reason:
it can dispatch none of them. Claude Code names its own credential in the
`account` block of `initialize` — `tokenSource` is the variable a bearer came
from and reads `none` when there is no bearer, and `apiKeySource` names an API
key when one is configured. Only an explicit `none` with no API key beside it
withholds. A signed-in subscription reports neither field, as does a Bedrock,
Vertex, or Foundry process resolving its credential through that cloud's own
chain; that silence is not a report of absence and withholds nothing.

For a withholding process the catalog comes from a fresh `list_models` rather
than the startup snapshot, which omits refused rows and predates Claude Code's
own gateway discovery — enabled by
`CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` — that lands after `initialize`
and is served from there. The adapter makes no request of its own to a gateway.

Menu absence never blocks a selection: the selected model is always offered as
the option's current value and is sent to Claude Code unchanged.

Discovery uses the credentials captured for the launched session, including
typed provider-auth injection. Starting the agent without credentials does not
cache missing credentials, so a later authenticated session can discover models.
Changing a provider binding invalidates the cache and fences earlier refreshes;
it does not replace credentials inside an already running Claude process.
Session start and native process relaunch each take a model-catalog snapshot.
Background cache refresh becomes visible through subsequent discovery.

The agent keeps an in-memory cache of at most 64 credential, endpoint, and
authentication-kind identities, keyed by a hash. Successful catalogs are fresh
for 10 minutes. Catalogs aged ten minutes to one hour return immediately while
one shared background refresh runs; transient failures may retain them only
within that hour from the successful read. A cold lookup waits at most three
seconds. Transport failures and HTTP 429/5xx can use bounded stale data;
HTTP 401/403, other HTTP failures, and malformed catalogs discard it. Failed
reads apply a 30-second retry cooldown. Cancelling a caller stops that caller's
wait; the shared fetch can finish for other sessions.
Logout, authentication changes, and agent close fence in-flight work. Catalogs
are not persisted.

`WithClaudeDirectAPI(false)` disables these Models API reads and the separate
setup-token quota probe. Native discovery continues when direct reads are
disabled, unavailable, or ineligible. Bedrock, Vertex, Foundry, custom
endpoints, ambiguous credentials, credential helpers, and native-home
authentication use native discovery; the catalog reader does not inspect native
credential files or execute helpers. Bare mode ignores OAuth,
so a setup token does not enable direct discovery there; an explicit API key
can still qualify. Adopting an API catalog
also requires readable native settings and a fresh native `list_models`
response so explicit restrictions can be preserved. HTTP reads refuse redirects
and bound pagination and response size.

### Host-listed models

A host that knows what its endpoint serves lists those ids with
`WithConfiguredModels`. Each id is published after the native rows on every
route as the id alone, with no metadata or effort levels, so a gateway session
carries a menu even before Claude Code's own discovery lands. An id Claude Code
already reports keeps its native row and facts, an id Claude Code refused stays
refused, and an id naming Anthropic's own model is withheld wherever the
conditions above withhold it. An empty, whitespace, or duplicate id fails
construction.

## Model and mode options

Session configuration uses typed option categories:

| Category | Examples |
| --- | --- |
| `model` | `model` |
| `mode` | permission mode and planning mode choices |
| `thought_level` | thinking budget choices |
| `model_config` | output style and structured output settings |

Use `session/set_config_option` with a selected option value. Boolean mode
payloads are rejected; clients should send the selected mode value.

`ANTHROPIC_MODEL` and `CLAUDE_MODEL_CONFIG` are read from the effective native
environment used for launch, including settings, static, and session overlays.
Managed sessions use the authority's base environment; ordinary sessions use
the ambient environment captured when the agent was constructed, from the
adapter's process or from `WithAmbientEnvironment`. Explicit empty
overrides remain empty.

### Defaults and storage

`WithDefaultModel("claude-fable-5-1")` sets the agent's `Options.DefaultModel`
launch default. A non-empty per-session `ClaudeOptions.Model` takes precedence.
Either becomes Claude's native `--model` argument, including on cold load or
resume. Without those explicit inputs, the adapter uses effective
`ANTHROPIC_MODEL`, then the model reported by native settings, with native
discovery supplying the default choice when no model is selected. A reused
live session keeps its current model until its configuration changes.

Claude also resolves `ANTHROPIC_DEFAULT_MODEL` as its default when higher-priority
model selections do not apply. The model-family variables `ANTHROPIC_DEFAULT_FABLE_MODEL`,
`ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL`, and
`ANTHROPIC_DEFAULT_HAIKU_MODEL` change the model behind their respective aliases.
A persisted native `model` setting stays in Claude's selected user, project,
local, managed, or overlay settings source. Native precedence and restrictions
still apply; see [Claude's model configuration](https://code.claude.com/docs/en/model-config#setting-your-model).

Storage follows the input's scope. Agent-wide defaults and environment remain
host construction inputs. Accepted per-session `ClaudeOptions.Env` and
`ExtraPathDirs` are stored in the `acp_session_configuration` row; a model
environment variable supplied through that session `Env` is therefore restored
with it. That row has no `model` field. The selected model lives in the active
adapter/native session, with durable native model information carried by the
mirrored transcript. `session/set_config_option` changes that live selection;
it does not write an adapter default-model preference. See [Session store](/docs/features/session-store).

Native `modelOverrides` settings remain Claude's dispatch responsibility. For
a choice named in those settings, API metadata requires an exact native row
with a resolved identity. The adapter does not guess whether that CLI version
recognizes the mapping or copy facts from a potentially redirected source ID.
Native labels and native facts remain intact.

Defaults and alias overrides are reconciled against each native process. They
do not become part of the provider catalog cache: that cache holds model facts
for a credential and endpoint, independently of any session's selected model.

### Custom model option

To add a native picker entry for Fable 5.1 with your chosen label, pass these
environment values before the native process starts:

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithEnv(map[string]string{
		"ANTHROPIC_CUSTOM_MODEL_OPTION":      "claude-fable-5-1",
		"ANTHROPIC_CUSTOM_MODEL_OPTION_NAME": "Fable 5.1",
	}),
)
```

`ANTHROPIC_CUSTOM_MODEL_OPTION_DESCRIPTION` optionally sets the description.
These variables add one selectable entry; they do not select it as the session
default. Native `availableModels` restrictions must permit the custom model ID.
Claude reads the variables at startup, so an existing native process must be
replaced to adopt changed values. See the official [custom model option
reference](https://code.claude.com/docs/en/model-config#add-a-custom-model-option).

When the same exact ID also appears in the Models API, the adapter keeps one
choice with the native custom label and description and adds the API token
limits and eligible effort values. Native effort restrictions and auto-mode
metadata still take precedence. A custom option also works through native
discovery when direct API discovery is disabled or ineligible.

## Image prompts

The adapter advertises standard ACP image prompt support
(`agentCapabilities.promptCapabilities.image`). That advertises transport only:
it does not claim that every selected model can interpret pixels or that Claude
has a native image generator. Model listings publish no per-model `capabilities`
array and no modality or generator fields.

The adapter also advertises the bounds it enforces under
`agentCapabilities._meta["acp-go.dev/mediaEnvelope"]`, so a host can check an
image before it sends one. See [Metadata](/docs/reference/meta).

Send a standard ACP image content block with embedded base64 `data` and one of
these exact media types:

- `image/png`
- `image/jpeg`
- `image/gif`
- `image/webp`

Images must be static. GIFs with multiple image descriptors, WebP with the
`ANIM` flag, and PNG with an `acTL` chunk are rejected before Claude starts, as
are missing or invalid base64, noncanonical media types, media-type/byte
mismatches, invalid dimensions, and configured byte-limit overflow. When a block
carries both `data` and `uri`, the embedded bytes are authoritative and the URI
is never fetched.

An embedded blob resource is gated the same way whatever its media type: its
base64 must decode strictly and its decoded size must fit the per-image byte
gate, and its bytes count toward the per-prompt total alongside image bytes. The
payload Claude receives is re-encoded from the bytes that passed the gates, so a
line-wrapped encoding reaches it in canonical form and an encoding with
non-canonical trailing bits is rejected `invalid_base64` rather than
reinterpreted. A text
resource is charged that same per-prompt total, so declaring bytes as text
rather than as a blob buys no extra budget. A blob declaring `application/pdf`
becomes a native document block, and the media type is matched after
normalization so `APPLICATION/PDF` and `application/pdf; charset=binary` reach
it too. A blob whose media type names a raster is validated as an image, so a
noncanonical declaration such as `IMAGE/PNG` is rejected `invalid_media_type`
rather than taking another path. A rejection names the block the bytes arrived
on: a resource block reports `prompt.resource` whichever gate chain ran.

## Handed-over prompt images

A host that shares a filesystem with the adapter can hand image bytes over as
local files instead of embedding base64, which keeps large multi-image turns out
of the ACP frame. Set the read root:

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithInputHandoffRoot("/srv/handoff"),
)
```

Then send an image block with empty `data`, a `file://` uri under that root, and
the handoff envelope carrying the payload's sha256 digest and byte size (the
exact `_meta` shape is in [Metadata](/docs/reference/meta)).

Everything decidable from the request alone is decided before the filesystem is
touched, first failure winning: the block and its envelope (`invalid_handoff`),
then the declared media type against the four-format allowlist
(`invalid_media_type`), then the declared `sizeBytes` against the effective
per-image byte gate (`too_large`). A block the adapter was never going to accept
therefore costs no filesystem access at all, and a rejected declaration reveals
nothing about whether the path it named exists.

Only then is the file opened, relative to the root with the operating system
enforcing containment as part of the open, so a path or symlink that leaves the
root is refused with no window between the decision and the read. A symlink
inside the root is followed only when its target is relative; an absolute
symlink is refused even when it points back inside. Anything that is not a
regular file — a directory, a FIFO, a device — is refused on the descriptor
rather than on the path, and the open never blocks waiting for a writer.

The read is bounded at one byte more than the block declared, not at the byte
gate: the work a block commits the adapter to is charged to the size its own
envelope stood behind. A file larger than it declares is
`handoff_digest_mismatch`, because it is not the file the declared digest covers.
Bytes that match the declared size and digest then pass the identical gate chain
an embedded image passes. A handed-over image and an embedded image carrying the
same bytes produce the same native request, and the host's path is never
forwarded to Claude.

Containment covers paths, not inodes: a process that can already write under the
root can hardlink a file into it from anywhere the adapter's user can read. The
declared digest is what makes handed-over bytes trustworthy, because a host that
cannot predict a file's contents cannot produce a block that will be accepted
for it.

The read is bounded even when `MaxInputBytesPerImage` is zero: the ACP frame
clamp becomes the ceiling, and a file past it is rejected `too_large` rather
than accepted with a digest that could not be verified. One prompt may hand over
at most 64 image files whatever the per-prompt byte total is set to; the block
that crosses that count is rejected `too_large` with the count as `sizeBytes`
and 64 as `maxBytes`, before it is read.

Files under the root belong to the host: the adapter only reads them, and the
host may delete one as soon as the prompt call returns. Without
`WithInputHandoffRoot` the form is rejected, so an image block with empty `data`
and no local uri stays a plain `missing_data` failure.

Claude Code exposes no authoritative selected-model modality field. Models API
capabilities do not control this gate, so a structurally valid image is
forwarded and the harness or provider stays authoritative for whether the
selected model can use those pixels.

Input failures use JSON-RPC `-32602 Invalid params`:

```json
{
  "field": "prompt.image",
  "error": "too_large",
  "index": 1,
  "sizeBytes": 6291457,
  "maxBytes": 6291456
}
```

The stable `error` values are `missing_data`, `invalid_base64`,
`invalid_media_type`, `media_type_mismatch`, `animated_not_supported`,
`invalid_dimensions`, and `too_large`, plus four for handed-over images:
`invalid_handoff` (the block itself is malformed, including an unset read root),
`path_not_allowed` (the path resolves outside the root or is not a regular
file), `missing_file` (a path inside the root that is gone or unreadable), and
`handoff_digest_mismatch` (the bytes do not match the declared digest or size).
The four handoff values carry a fixed `message` naming the cause, never a path,
a digest, or an observed byte count. A `handoff_digest_mismatch` reports one
message whether the size or the digest disagreed, so the envelope cannot be
swept to measure a file, and it always fails the turn rather than falling back
to another form. A blob-resource rejection reports `field` `prompt.resource`.

`index` counts the blocks the byte gates apply to, in request order: image
blocks and every gated blob resource whatever its media type. Text, resource
links, and text resources consume no index. Validation stops at the first
failing prompt block, and an aggregate overflow is attributed to the block that
crosses the total.

## Image limits

All four decoded-byte policy limits default to 6 MiB:

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithImageLimits(claudeacp.ImageLimits{
		MaxInputBytesPerImage:     6 * 1024 * 1024,
		MaxInputBytesPerPrompt:    6 * 1024 * 1024,
		MaxOutputBytesPerImage:    6 * 1024 * 1024,
		MaxOutputBytesPerToolCall: 6 * 1024 * 1024,
	}),
)
```

Supplying `WithImageLimits` replaces the whole struct. A zero field disables
that specific adapter policy limit; a negative field is a refused construction
option, so every entry point answers `-32603 Internal error` with
`{"error":"claude_invalid_options"}` — the caller's parameters were valid and
the agent the host built is what cannot serve them. A construction verdict is
never `-32602`: nothing is wrong with the request. See
[Internal errors](/docs/reference/acp-methods#internal-error-contract).

Zero never bypasses the hard ACP frame
bound that limits one emitted image. Typed image output and its durable replay
are covered in [Session store](/docs/features/session-store).

## Custom Anthropic-compatible base URL

To point Claude Code at a custom Anthropic-compatible endpoint, set the base URL
through the environment. Claude Code reads `ANTHROPIC_BASE_URL` (and related
`ANTHROPIC_*` variables), so pass it with `WithEnv`. Such a session publishes
what the endpoint serves rather than Anthropic's model names — see
[Routing and credentials decide which names are published](#routing-and-credentials-decide-which-names-are-published).

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithEnv(map[string]string{
		"ANTHROPIC_BASE_URL": "https://anthropic.internal.example",
	}),
)
```

`WithSeedFiles` is not the mechanism for the base URL — it seeds
`settings.json`-style config files into the resolved Claude config directory
(for example, a curated `settings.json` `env`, `permissions`, or
`availableModels` block). Because the seed anchor is the `CLAUDE_CONFIG_DIR`
root that Claude Code reads directly, seeding **requires an explicit `WithHome`
(`-home`)**: if `WithHome` is unset, session start fails closed with the uniform
invalid-parameters error rather than writing into the operator's default
`~/.claude`. Keep secrets in `WithEnv` and reference them from seeded files by
environment-variable name.

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithHome("/tmp/claude-home"),
	claudeacp.WithEnv(map[string]string{
		"ANTHROPIC_BASE_URL": "https://anthropic.internal.example",
	}),
	claudeacp.WithSeedFiles(map[string]string{
		"settings.json": `{"env":{"ANTHROPIC_BASE_URL":"https://anthropic.internal.example"}}`,
	}),
)
```

### Seed-file provenance guard

Seed writes never overwrite a file the adapter did not create. The adapter
tracks the files it owns in a per-config-dir manifest (`.seed-manifest.json`,
a JSON array of managed relative paths). Before writing each seed file:

- If the target does not exist, it is written and recorded in the manifest.
- If the target exists and is already in the manifest, it is overwritten, keeping
  a `.seed.bak` copy of the prior bytes when the content changes (identical
  bytes are left untouched).
- If the target exists and is **not** in the manifest — an operator-authored
  file — session start fails closed with the uniform invalid-parameters error
  naming the offending path, and nothing on disk is changed.

## Native settings overlay

Prefer a namespaced settings overlay over overwriting the base `settings.json`.
`WithClaudeSettingsFile(relpath)` resolves a path under the effective Claude
config directory (the same anchor as `WithSeedFiles`, so it also **requires an
explicit `WithHome`**) and passes it to the Claude CLI as `--settings <abspath>`.
Claude loads that file as an additional settings layer on top of the base
`settings.json` rather than replacing it.

```go
err := claudeacp.Serve(ctx, input, output,
	claudeacp.WithHome("/tmp/claude-home"),
	claudeacp.WithSeedFiles(map[string]string{
		"custom.settings.json": `{"env":{"ANTHROPIC_BASE_URL":"https://anthropic.internal.example"}}`,
	}),
	claudeacp.WithClaudeSettingsFile("custom.settings.json"),
)
```

Seed the namespaced overlay and point `--settings` at it instead of overwriting
the base `settings.json`. Setting `WithClaudeSettingsFile` without a resolvable
`WithHome`, or with an absolute path or a `..` escape, fails closed at session
start. (Claude's LiteLLM-style routing is normally pure-env; this overlay is for
`settings.json`-style config.)
