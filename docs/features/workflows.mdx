Claude Code can launch its native `Workflow` tool to coordinate staged
subagent work. This adapter keeps `Workflow` visible as a normal ACP tool call
and adds Claude-specific workflow details under `_meta.claude.workflow`.

Workflows are a Claude-specific incubation surface. Portable clients should
render the standard ACP `tool_call` and `tool_call_update` fields first, then
use `_meta.claude.workflow` only when they want richer workflow topology.

## Capability

The initialize response advertises workflow mapping support:

```json
{
  "claude": {
    "workflows": {
      "updates": true,
      "scope": "session",
      "toolKind": "think",
      "metadataPath": "tool_call_update._meta.claude.workflow",
      "logs": {
        "readByDefault": false
      },
      "rawEvents": "_claude/sdkMessage"
    }
  }
}
```

No workflow management extension methods are exposed yet. Progress is delivered
through normal ACP session updates.

## Tool Updates

Claude's `Workflow` tool is mapped as `ToolKindThink`, matching Claude's
existing subagent launchers. `task_started` marks the tool call in progress.
Later `task_progress`, `task_updated`, and `task_notification` frames update the
same tool call.

Successful Claude launch results with `async_launched` or `remote_launched`
stay in progress; they are not mapped as completed tool results. Launch or
review failures with `is_error: true` still use the normal failed tool-result
path.

Terminal workflow statuses map to ACP tool-call status as follows:

| Claude status | ACP status |
| --- | --- |
| `completed` | `completed` |
| `failed` | `failed` |
| `stopped` | `failed` |
| `killed` | `failed` |
| `pending`, `running`, `paused` | `in_progress` |
| unknown | metadata only |

The Claude status is still preserved in `_meta.claude.workflow.status`.

## Metadata Shape

Workflow metadata is an accumulated snapshot, not only the latest Claude delta:

```json
{
  "claude": {
    "toolName": "Workflow",
    "workflow": {
      "taskId": "task-123",
      "runId": "run-123",
      "workflowName": "review-plan",
      "summary": "Review finished",
      "status": "completed",
      "usage": {
        "total_tokens": 1234
      },
      "phases": [
        {
          "type": "workflow_phase",
          "index": 1,
          "title": "Review"
        }
      ],
      "agents": [
        {
          "type": "workflow_agent",
          "index": 1,
          "label": "reviewer",
          "phaseIndex": 1,
          "phaseTitle": "Review",
          "agentId": "agent-123",
          "state": "done",
          "resultPreview": "No blocking findings."
        }
      ],
      "activeAgents": 0,
      "completedAgents": 1,
      "failedAgents": 0
    }
  }
}
```

`phases` are merged by `index`. `agents` are also merged by `index`, matching
Claude Code's own reducer; `agentId` is retained as payload metadata but is not
used as the merge key because queued start frames can omit it.

Sparse Claude deltas retain earlier fields. For example, a later agent `done`
frame that omits `agentId` keeps the `agentId` observed in a previous progress
frame for the same index.

Agent state counts are derived from accumulated `workflow_agent.state` values:

| Agent state | Count bucket |
| --- | --- |
| `start`, `progress` | `activeAgents` |
| `done` | `completedAgents` |
| `error` | `failedAgents` |

Unknown agent states are preserved but do not affect counts.

## Raw Events

Enable [raw Claude events](/docs/features/raw-events) when you need to inspect
provider-native workflow frames or debug Claude CLI drift. Raw events may
include `task_started`, `task_progress`, `task_updated`, `task_notification`,
and the original `Workflow` launch result.

Normal mapped updates remain available whether raw events are enabled or not.

## Logs And Files

Claude workflow frames can include references such as `transcriptDir`,
`scriptPath`, and `output_file`. The adapter may expose those paths and
availability flags in metadata, but it does not read or stream those files by
default.

Full workflow logs can contain subagent prompts, tool output, file paths,
secrets, and other sensitive context. Any future log-reading feature should be
an explicit opt-in extension with truncation, redaction, and security review.

## Permissions

Inline dynamic workflows can trigger Claude's review gate. With the adapter's
`--permission-prompt-tool stdio` path, that gate is surfaced as
`session/request_permission` for the `Workflow` tool.

When a named Workflow allow-always suggestion would persist a project-local
Claude rule, the adapter normalizes that suggestion to session scope. This keeps
Workflow permissions aligned with the adapter's session-scoped permission
posture.
